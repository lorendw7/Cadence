# Repository instructions

## Documentation

- Write all repository documentation in plain English. This applies to new and updated files, including READMEs, design documents, lesson notes, maintenance guides, and generated asset documentation.
- Use short sentences, familiar words, and concrete examples. Explain technical terms when they first appear.
- Keep product translations separate from documentation. The website and future app may use Japanese, English, and Chinese. Do not remove those translations when editing documentation.
- Keep document paths stable. Update the documentation index and local links when adding or moving a document.
- Keep personal funding applications, pitch scripts, interview practice, translations of those materials, and private correspondence outside this product repository. A general request to organize documentation or push main does not authorize publishing them; require an explicit request to publish those specific materials.
- Separate implemented behavior, planned work, historical lesson results, and checks that still need a person to confirm them. Never describe a plan or a passing build as a released feature.

## Learning and implementation

- The learner writes learning-critical core code: data rules, state changes, async failure decisions, and the first representative Dart and Flutter implementations. Explain one small lesson at a time; review the learner's code and provide relevant tests. Core practice includes widgets, layout, callbacks and lifecycle, not only business functions.
- Keep `lib/main.dart` as the teaching entry. Do not implement future lessons, add unused packages, or create empty architecture layers.
- Under the learner's standing delegation, the assistant may complete supporting work for the current lesson: repeated wiring and components, visual polish, translation wiring, test setup and broader regressions, build checks, documentation, artwork, the website, and behavior-preserving cleanup. State the learner-owned code and support boundary before editing; no repeated permission is needed for that supporting work.
- A new business rule, state owner, lifecycle decision or save/failure contract is learning-critical even when it appears inside supporting code. Keep it in the learner's small exercise unless explicitly delegated. Do not turn the exercise into isolated blanks or count assistant-written code as independent mastery. See `docs/CURRICULUM.md` for the division of work and Dart/Flutter practice.
- Current progress belongs in `docs/LEARNING.md`. Lesson notes keep their historical results. Product scope belongs in `docs/PRODUCT.md` and release gates in `docs/ROADMAP.md`.

## Design and delivery

- Preserve the independent academic-journal identity and website source. The maintainer approved taking Pages offline on 2026-11-15. On 2026-11-27 they chose to reopen the source and the concept site on GitHub Pages under ADR-016; until the repository is public and Pages is enabled, the site stays offline. Future server deployment is deferred; do not buy or configure hosting without a separate request.
- Cadence is a local time-management and planning app for work, study, and daily life. Under ADR-015, Android self-use is the first delivery target, with Windows as the development host. Build safe shared tasks and recovery, then direct plans, Today and a selected-day Week view, then a bounded task-linked Android focus countdown with manual breaks and local records. Test native storage and lifecycle on the phone; a complete Windows release is not a prerequisite. Desktop compact mode, media integration and Steam are later work. Keep one shared Flutter codebase; iOS, macOS/Linux and Web need separate acceptance. Screenshot and CSV/table import remain deferred. School authorization, applications and implementation are explicitly postponed; any later access needs school permission and a documented data route, with no school passwords or scraping. Cloud sync remains deferred. Desktop, Web and the concept site stay ad-free; mobile ads need a useful release and a separate later pilot.
- Keep the Android self-use edition ad-free and assume no income funds its development. A one-time desktop purchase and later mobile-only ads remain revenue hypotheses, with no price or paid release approved. No subscriptions, paid capacity, paid priority or ad-based feature unlocks are planned. Any future cloud quota remains uniform. Count development and support time in cost recovery. See docs/adr/015-android-self-use-first.md and the retained commercial limits in ADR-014.

Keep the phone focus phase to one task-linked countdown, manual breaks and local records. Defer count-up, automatic cycles, checklists, ambient mixing, extra scenes/themes and Wallpaper Engine. A budget review does not itself authorize spending.

Do not describe preparation as a submitted application, approved access or implemented integration. Authentication permission and timetable-data permission are separate.
